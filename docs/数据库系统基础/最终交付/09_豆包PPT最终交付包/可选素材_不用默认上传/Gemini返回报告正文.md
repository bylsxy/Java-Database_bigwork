## 第一章 引言

### 1.1 项目背景

随着数字摄影设备的普及与 AI 图像生成技术的飞速发展，个人电脑中积累的数字图像数量呈指数级增长。传统的基于操作系统文件资源管理器的图片管理方式，仅能依赖离散的文件夹层级和简单的文件名进行粗粒度检索，无法满足海量图片在语义检索、多维特征筛选、版本追溯以及结构化统计等方面的深度需求。

本项目旨在打破“图片仅作为文件存储”的传统范式，引入关系型数据库（PostgreSQL）作为底层核心枢纽，将本地图片目录转化为可持久化、可检索、可审计、可扩展的数据资产。通过构建《基于 PostgreSQL 的数字图像集成管理系统》（Digital Image Integrated Management System, DIMS），系统不仅接管图片的物理信息（路径、大小、格式），更深入挖掘并结构化存储图片的语义特征（AI 标签、描述、版本历史、编辑记录），从而实现从“文件管理”到“数据模型驱动的数据资产管理”的跨越。

### 1.2 系统目标

本系统致力于为个人电脑“机主”提供一套轻量级、高性能、智能化的桌面端图像管理解决方案。具体目标包括：

1. **数据结构化与持久化**：使用 PostgreSQL 严谨存储目录树结构、图片元数据及缩略图（`bytea`），实现数据的统一完整性管理。
2. **多维高效检索**：突破纯文本搜索，支持多维条件组合及自然语言转 SQL（NL2SQL）的高级检索模式。
3. **智能语义标注**：集成 AI 大模型接口，自动生成结构化图片标签，并持久化于关系数据库中以供查询。
4. **无损版本控制**：借鉴数据库事务与版本理念，对图片编辑操作进行留痕，支持多版本的快速切换与回滚。
5. **健壮的离线可用性**：系统以本地数据库为核心，在无网络或 AI 接口熔断时，仍能提供完整的本地图片浏览与数据修改能力。

### 1.3 用户范围与系统边界

* **用户范围**：系统面向单一终端的个人电脑“机主”。用户需具备基本的桌面软件使用能力，对图片分类、检索及轻度编辑有较高要求。
* **系统边界**：本系统属于本地运行的 JavaFX 桌面客户端应用，强依赖于本地部署或局域网内的 PostgreSQL 数据库实例。核心管理范围限定于用户主动纳入扫描的本地磁盘目录。系统支持接入外部 AI 服务（OpenAI-compatible endpoints）以增强标签识别能力，并预留了 WebDAV 等云端存储的扩展数据表，但现阶段核心主流程仍聚焦于本地关系型数据的强一致性管理。

## 第二章 需求分析

### 2.1 系统范围与功能需求

根据《需求分析word正式版.doc》及教师任务书约束，本系统必须是一个重度依赖数据库操作的应用程序，其核心功能需涵盖对数据的增、删、改、查，不可仅退化为简单的文件浏览器。系统核心功能范围如下：

1. **目录与图片发现模块**：支持对本地磁盘目录的扫描、监听与懒加载；将物理文件信息映射为数据库实体记录。
2. **结构化视图模块**：提供基于数据库查询结果的缩略图网格展示，支持按照图片活跃度、格式、大小等维度进行动态过滤与排序。
3. **智能标签与搜索模块**：涵盖传统关键词模糊查询（基于 `pg_trgm`）、条件组合查询及 NL2SQL 查询。支持对 AI 识别结果的持久化存储与标签的多对多管理。
4. **图片编辑与版本模块**：提供图片的裁剪、旋转等编辑功能，每次保存均作为新版本写入数据库，支持查看编辑历史并执行数据回滚。
5. **批量事务操作模块**：支持对多张图片在同一数据库事务下进行批量重命名、批量删除或批量打标签，确保原子性。
6. **系统配置与状态反馈模块**：系统初始化时的数据库建库建表引导，AI 供应商链路测试及熔断降级（Circuit Breaker）机制的配置存储。

### 2.2 系统功能结构与总体流程

### 2.3 数据字典

数据字典旨在从用户视角定义系统中所流通的核心数据项，是建立实体关系模型（ER）的基础。

#### 2.3.1 实体数据项定义

* **图片元数据 (Image Metadata)**：图片对象的核心描述。
* *数据项*：图片ID (自增主键)、文件名 (最大100字符)、文件路径 (绝对路径)、文件大小 (Byte)、宽度 (Pixel)、高度 (Pixel)、格式 (JPG/PNG等)、SHA-256哈希值 (唯一标识)、缩略图 (二进制流)、AI处理状态 (布尔值)、创建时间、最后修改时间、删除标记 (软删除逻辑)。


* **目录节点 (Directory Node)**：组织图片的层级容器。
* *数据项*：目录ID (自增主键)、目录名称、物理路径 (唯一约束)、父目录ID (递归外键)。


* **标签类别 (Tag Category)**：对标签进行的顶层业务分类。
* *数据项*：类别ID、内部标识名 (英文)、显示名称 (中文，如“人物”、“风景”)、分类描述。


* **智能标签 (AI Tag)**：最小的语义标识单元。
* *数据项*：标签ID、标签名称 (如“日落”、“猫”)、所属类别ID、标签热度/使用频次。


* **图片版本 (Image Version)**：单次编辑产生的数据快照。
* *数据项*：版本ID、图片ID (外键)、版本号 (整型递增)、版本文件路径、缩略图、编辑类型 (如“裁剪”、“旋转”)、描述、是否当前版本、创建时间。


* **AI 分析结果 (AI Analysis Result)**：大模型返回的完整结构化感知数据。
* *数据项*：结果ID、图片ID、完整自然语言描述、预估人数、使用的模型名称、原始 JSON 响应 (用于追溯)、分析时间。


* **操作日志 (Operation Log)**：审计追踪数据。
* *数据项*：日志ID、图片ID、操作类型 (新增、删除、重命名等)、旧值快照、新值快照、操作时间。


* **应用设置 (App Setting)**：系统运行参数。
* *数据项*：配置键 (Key)、配置值 (Value)、配置描述、最后更新时间。


* **搜索历史 (Search History)**：用户检索行为留存。
* *数据项*：历史ID、查询文本、搜索模式 (关键词/NL2SQL)、生成的底层 SQL (若有)、返回结果数、查询时间。



#### 2.3.2 界面视图数据组成

* **主界面的图片网格展示单元** = 图片缩略图流 + 文件名 + 文件大小 + 图像分辨率。
* **图片属性详情面板** = 基本物理信息 + 所属目录路径 + 关联的 AI 标签集合（以逗号分隔）+ 完整 AI 描述文本。
* **系统月度报表** = 统计月份 + 新增图片数 + 新增存储占用 + AI 识别覆盖率 + 活跃修改记录数。

## 第三章 数据库设计

数据库设计是本课程设计的核心（评分占比 30%）。本系统充分利用了 PostgreSQL 18.3 的高级特性，规避了将其仅仅作为“轻量级 KV 存储”的误区。系统的底层涵盖了完整的表结构、严密的约束体系、高效的索引树以及活跃的数据库对象（视图、触发器、存储过程）。

### 3.1 实体来源与 ER 关系模型

实体关系直接映射自需求分析中的数据字典。核心业务实体间存在如下关系：

1. **目录与目录 (Directories)**：1 对 N 的自引用关系，构建目录树。
2. **目录与图片 (Directories - Images)**：1 对 N 关系，一个目录包含多张图片。
3. **图片与标签 (Images - Tags)**：M 对 N 关系，通过关联表 `image_tags` 实现。一张图片有多个标签，一个标签贴在多张图片上。
4. **标签类别与标签 (Tag_Categories - Tags)**：1 对 N 关系，对零散的标签进行业务归类。
5. **图片与版本 (Images - Versions)**：1 对 N 关系，一张原图对应多个历史编辑版本。
6. **图片与 AI 结果 (Images - AI_Results)**：1 对 1 关系，保存大模型对单张图片的综合描述。
7. **图片与日志 (Images - Operation_Logs)**：1 对 N 关系，记录该生命周期内的所有核心变更。

### 3.2 关系模式（表结构）与物理结构设计

系统根据第三范式（3NF）设计，彻底消除了数据冗余。根据 `schema.sql` 中的真实定义，当前系统共建立 **13 张表**。

#### 3.2.1 核心表定义与约束策略

以下为主要核心表的模式说明及空值（NULL）控制策略设计：

**1. 目录表 (`directories`)**

* *设计考量*：用于构建文件系统的层级结构。`parent_id` 允许为空（NULL），当且仅当该记录为根目录时为空。通过自引用实现树状结构。
* *字段*：`id` (SERIAL PK), `dir_name` (VARCHAR(255) NOT NULL), `dir_path` (TEXT UNIQUE NOT NULL), `parent_id` (INT FK 关联自身)。

**2. 图片元数据表 (`images`)**

* *设计考量*：全系统的中枢表。记录软删除状态 `is_deleted` 以支持回收站功能。存储 SHA-256 `file_hash` 预防重复记录。
* *空值率分析*：大部分基础字段具有 `NOT NULL` 约束。`thumbnail`（缩略图 bytea）在生成期间或损坏时允许为空（空值率预期 < 1%）。`last_ai_scan` 在未被 AI 调度前为空（空值率随后台扫描进度动态归零）。
* *字段*：`id` (SERIAL PK), `file_name` (VARCHAR(255) NOT NULL), `file_path` (TEXT UNIQUE NOT NULL), `directory_id` (INT FK NOT NULL), `file_size` (BIGINT NOT NULL), `width` (INT NOT NULL), `height` (INT NOT NULL), `format` (VARCHAR(10)), `thumbnail` (**BYTEA**), `file_hash` (VARCHAR(64)), `ai_processed` (BOOLEAN DEFAULT FALSE), `is_deleted` (BOOLEAN DEFAULT FALSE), `created_at` (TIMESTAMP), `modified_at` (TIMESTAMP)。

**3. 标签分类表 (`tag_categories`) & 标签表 (`tags`)**

* *设计考量*：规范化标签管理。
* *字段*：`tags` 表包含 `id` (SERIAL PK), `name` (VARCHAR(100) UNIQUE NOT NULL), `category_id` (INT FK NOT NULL)。

**4. 图片标签关联表 (`image_tags`)**

* *设计考量*：多对多关系解析表，使用复合主键 `(image_id, tag_id)` 以防止同一图片被打上重复标签。

**5. AI 分析结果表 (`ai_analysis_results`)**

* *设计考量*：保存大模型原始响应和解析结果。其中 `raw_response` 字段采用 PostgreSQL 强大的 **JSONB** 格式存储，以便未来进行非结构化数据的快速抽取与全文检索。
* *字段*：`id` (SERIAL PK), `image_id` (INT UNIQUE FK), `description` (TEXT), `people_count` (INT), `model_used` (VARCHAR(50)), `raw_response` (**JSONB**)。

**6. 图片版本表 (`image_versions`)**

* *设计考量*：保存编辑器保存的历史快照，`is_current` 标志用于快速定位当前激活的版本。

其他辅助表包含：`operation_logs` (操作审计), `app_settings` (K-V 配置), `search_history` (搜索习惯分析), `image_edit_operations` (笔刷级记录), `cloud_sources` 与 `cloud_images` (为未来云端存储预留的挂载点)。

### 3.3 外模式设计（视图）

为简化应用程序（控制器层）的 SQL 复杂度，并向最终用户屏蔽底层物理表的关联细节，系统建立了 **4 个视图**。

1. **活跃图片视图 (`v_active_images`)**：
* *用途*：应用程序主界面最常用的视图，自动过滤掉 `is_deleted = TRUE` 的软删除记录。


2. **目录统计视图 (`v_directory_stats`)**：
* *用途*：为左侧树形导航栏提供数据支撑，预聚合了各个目录下拥有的活跃图片数量及占据的存储总大小。


3. **多维标签宽表视图 (`v_image_search`)**：
* *用途*：用于复杂检索（如关键词聚合搜索）。该视图使用 `STRING_AGG` 将一张图片对应的多条标签记录合并为一个逗号分隔的字符串，并联表获取 AI 长文本描述。


4. **标签统计视图 (`v_tag_stats`)**：
* *用途*：为“设置-标签清理向导”提供决策支持，统计每个标签被多少张存活图片所引用。



### 3.4 性能优化与索引设计

针对读多写少的图片浏览场景，系统构建了 **19 个索引**。以下列出最具代表性的几类索引设计依据：

1. **层级导航加速**：
* `CREATE INDEX idx_directories_parent_id ON directories (parent_id);`
* *理由*：目录树的展开极其频繁，该索引使得获取子目录的时间复杂度从 O(N) 降为 O(1)。


2. **状态过滤加速**：
* `CREATE INDEX idx_images_active ON images (directory_id) WHERE is_deleted = FALSE;`
* *理由*：**部分索引（Partial Index）** 的经典应用。系统几乎不会查询已删除的图片，部分索引体积更小，内存命中率极高。


3. **模糊搜索加速**：
* `CREATE INDEX idx_tags_name_trgm ON tags USING gin (name gin_trgm_ops);`
* `CREATE INDEX idx_ai_desc_trgm ON ai_analysis_results USING gin (description gin_trgm_ops);`
* *理由*：用户输入搜索词通常是不精确的。结合 PostgreSQL 扩展插件 `pg_trgm`，使用 **GIN（倒排索引）** 加速基于三元组的 `LIKE '%关键词%'` 操作，其性能远超全表扫描。


4. **外键级联加速**：为所有作为外键的字段（如 `idx_image_tags_tag`, `idx_versions_image`）建立 B-Tree 索引，避免在执行删除操作时引发全表锁定。

### 3.5 数据库活动对象（触发器与存储过程）

为保障数据的绝对一致性，将部分计算逻辑下沉至数据库层，本系统共部署了 **5 个触发器** 和 **5 个存储过程/函数**。

#### 3.5.1 触发器（Triggers）与触发器函数

触发器负责接管底层的级联状态维护，防止应用层代码遗漏或出现并发漏洞：

1. **自动时间戳维护**：
* `trg_image_before_update`：触发 `fn_update_modified_at()` 函数。在执行任何 `UPDATE images` 语句前，自动将 `modified_at` 刷新为 `NOW()`。


2. **AI 处理状态联动标记**：
* `trg_image_after_insert` 和 `trg_image_after_delete`：联动触发 `fn_log_image_change()`，自动向 `operation_logs` 写入生命周期节点。


3. **标签热度统计维护**：
* `trg_tag_after_insert` / `trg_tag_after_delete`：当 `image_tags` 发生增删时，自动触发函数重新计算目标标签的热度。



#### 3.5.2 存储过程（Stored Procedures）

存储过程用于封装复杂的业务事务，确保多个 SQL 语句在同一个原子上下文中执行。

1. **图片版本回滚 (`sp_restore_version`)**：
* *逻辑*：接收 `image_id` 和目标 `version_num`。首先将 `image_versions` 表中对应记录设为 `is_current = TRUE`，其余设为 `FALSE`；随后将目标版本的文件路径和缩略图数据回写覆盖到主 `images` 表；若任一步骤失败，则引发事务异常回滚。


2. **批量安全重命名 (`sp_batch_rename`)**：
* *逻辑*：由于操作系统的文件重命名可能因权限问题中断，该存储过程在游标中逐条更新数据库的 `file_path` 和 `file_name`，结合 Java 侧的事务捕捉，若文件系统重命名失败，则通过抛出 SQLException 中止并回滚整批操作。


3. **报表与统计过程**：包含 `sp_monthly_report`（用于生成月度审计快照）、`sp_directory_report` 以及 `sp_batch_insert_tags`（用于 AI 识别后多标签并发入库的冲突处理）。

### 3.6 PostgreSQL 技术选型深度理由

在项目初期论证中放弃 MySQL 与 SQLite，坚定选择 PostgreSQL 18.3 的核心依据在于其在非传统关系型数据处理上的统治力：

1. **`BYTEA` 类型的卓越支持**：系统将成千上万个 20KB~50KB 的缩略图直接灌入数据库。PostgreSQL 的 TOAST (The Oversized-Attribute Storage Technique) 机制在处理 `bytea` 时表现优异，避免了外置文件系统带来的碎文件夹问题，同时保证了“图片+缩略图”备份恢复的一致性。
2. **递归 CTE (Common Table Expressions) 处理目录树**：目录结构的任意深度遍历是业务痛点。利用 `WITH RECURSIVE` 语法，用一条查询语句即可无缝穿透获取指定目录下所有的子孙文件夹，完全规避了在 Java 层进行低效递归查库。
3. **JSONB 语义兼容**：大模型（AI）的返回结果格式具有多变性。采用 `JSONB` 字段暂存大模型的 `raw_response`，既保证了扩展性，又可通过 PG 的 JSON 路径操作符直接查询内部键值对，无需二次解析。

## 第四章 系统设计与实现

### 4.1 总体架构设计

本系统采用 Java 21 作为开发语言，前端 GUI 使用 JavaFX 21.0.6 构建。整体应用严格遵循**经典三层架构体系**，模块间耦合度低，易于单测与功能扩展。
[图6_后台架构图.png]

1. **表示层 (View/Controller)**：
使用 FXML 声明式布局界面，结合 JavaFX CSS 渲染暗色/亮色主题。Controller（如 `MainController`）仅负责事件绑定、UI 线程刷新及弹窗调度。
2. **业务逻辑层 (Service)**：
包含 `ImageServiceImpl`, `SearchService`, `AiTagStorageService` 等。负责编排操作流程，例如在 `ImageService.renameImage` 中同步调用操作系统 `Files.move` 与 DAO 的 `update` 方法，保证双写一致。
3. **数据访问层 (DAO)**：
如 `ImageDaoImpl`, `TagDaoImpl`。隐藏 JDBC 细节，所有的 SQL 拼接与参数传递均在此层完成。

### 4.2 数据库连接池与 JDBC 性能调优

为了保障桌面端应用在高并发扫描时的流畅性，系统摒弃了低效的单例直连，引入了企业级连接池 **HikariCP (v6.2.1)**。

* **连接池管理 (`DatabaseConnection.java`)**：系统启动时全局初始化 `HikariDataSource`，配置 `maximumPoolSize` 避免耗尽桌面系统资源。
* **资源释放严谨性**：严格遵守 `try-with-resources` 语法块。在 `ImageDaoImpl` 等所有 DAO 中，`Connection`, `PreparedStatement` 和 `ResultSet` 的作用域被绝对封闭，杜绝游标泄露。
* **防止 SQL 注入**：全系统禁绝 `Statement` 字符串拼接查询。对于任何带有用户输入的参数（如搜索关键词、重命名文本），一律使用 `PreparedStatement` 占位符 `?` 传参，由 PG 驱动完成安全转义。

### 4.3 核心业务模块实现与亮点

#### 4.3.1 完整磁盘目录树懒加载与后台扫描

针对用户磁盘可能包含深层嵌套目录，若一次性加载会导致 UI 假死。系统在左侧 `TreeView` 中采用**懒加载 (Lazy Loading)** 模式。
仅当用户点击展开箭头时，程序才向数据库发起针对 `parent_id = 当前节点` 的查询，毫秒级响应。
同时，底层 `DirectoryScanner` 与 `ScanTask` 基于 `java.nio.file.Files.walkFileTree` 构建。Task 在 JavaFX 后台线程池独立运作，并通过 `updateProgress` 方法实时向主界面的状态栏进度条推送更新。

#### 4.3.2 智能 AI 标签与断路器机制 (Circuit Breaker)

AI 解析是系统的亮点。`ScanTask` 提取图片信息后，调用 `OpenAICompatibleService` 向外部大模型发送 Base64 缩略图并请求 JSON 格式响应。由于网络 API 的不稳定性，系统在 `AIFallbackManager.java` 中引入了严密的熔断与降级策略：

* 用户可在设置面板配置多个供应商节点（Endpoint）。
* 当主节点连续抛出 `IOException` 达到阈值时，`AIFallbackManager` 触发**熔断**，静默将请求重定向至备用节点（Fallback），有效避免系统因超时而长时间阻塞本地入库线程。

#### 4.3.3 NL2SQL 搜索机制

常规的过滤条件通常是硬编码的表单提交。本系统实现了 NL2SQL 搜索（Natural Language to SQL）。
当用户在搜索框输入“*找出上个月在北京拍的、带猫的图片，并且文件大于 5MB*”时，`SearchService` 拦截此请求，结合数据库预留 Schema 作为提示词上下文，请求大模型生成一条严谨的只读 `SELECT` SQL。为防止越权攻击，系统对生成的 SQL 实施“前端拦截+独立只读数据库用户”的双重安全检验机制，确保最终在 `images` 与 `tags` 上执行的只读过滤是绝对安全的。
[图5_NL2SQL安全链路.png]

#### 4.3.4 一键数据库初始化向导

极大地提升了桌面软件的用户体验。考虑到部分用户计算机尚未配置好数据库环境，系统入口被 `DatabaseBootstrapService` 接管。
当检测到无法连接数据库或 `images` 表不存在时，自动弹出 `DatabaseSetupDialog` 初始化向导。用户仅需填入本机 PostgreSQL 管理员凭证，程序自动发送 `CREATE DATABASE image_manager` 并在新库中按序无缝执行内嵌的 `schema.sql` 和 `data.sql`，彻底免除了用户手动使用 `psql` 导入脚本的痛苦。
[real_08_数据库连接与初始化向导_760x680.png]

### 5.1 UI/UX 设计理念

界面完全采用 JavaFX 构建，抛弃原生灰阶风格，全面注入深色（Dark Mode）与流体响应式设计。界面的左右分栏与状态栏设计向专业资产管理软件对齐，注重信息的密集呈现与操作的直观性。

### 5.2 核心界面展示

1. **主界面与缩略图网格**：左侧为无限层级的目录树，中间为图片流，支持多选、框选操作；右下角呈现异步处理任务进度。
[real_02_主界面_1200x800_默认窗口.png]
2. **图片编辑器与版本控制**：点击单张图片进入详情与编辑页。编辑器支持图像翻转、裁剪、滤镜叠加。右侧时间轴显示该图片的历史版本，一键即可调用数据库存储过程完成版本回滚与重制。
[real_14_图片编辑器_1250x938.png]
3. **幻灯片播放模块**：基于 `Media` 和 `Timeline` 类实现的增强播放器。用户框选多图后启动，系统支持全屏自适应比例播放，且支持在后台混音播放 BGM 音乐。

4. **系统设置与 AI 配置页**：提供详细的存储空间占用报告（自动从 `pg_total_relation_size` 中提取数据库容量），并管理大模型 Endpoint 及其连通性测试。

### 5.3 演示验证路线与测试覆盖

我们制定了严密的测试验证逻辑，重点针对“数据库功能是否真实验证生效”进行覆盖：

* **连通性测试**：故意输入错误的数据库密码，向导正确拦截并抛出错误；更正密码后，成功建库，验证了 `DatabaseBootstrapService` 的鲁棒性。
* **事务回滚测试**：在进行 10 张图片的批量重命名时，人为使第 8 张图片的系统文件只读，导致抛出文件异常。观测数据库，发现前 7 张在内存中成功重命名的记录被完美回滚，证明 JDBC 事务 (`conn.rollback()`) 机制生效，防止了数据撕裂。
* **复杂视图查询测试**：向系统中打入上万张测试记录。借助 `idx_tags_name_trgm` 倒排索引，执行搜索任务的响应时间稳定在 50ms 内，相较未建索引的全表扫描（约 1200ms）实现了数量级的性能飞跃。

## 第六章 安装与使用说明

### 6.1 运行环境要求

1. **底层环境**：安装有 Java 21+ 运行环境 (JRE/JDK)。
2. **数据中心**：本机或局域网需运行 PostgreSQL 服务（版本不低于 15，本项目于 18.3 验证）。
3. **可选服务**：有效的 OpenAI-compatible API Endpoint 及对应 API Key，用于激活智能视觉标签功能。

### 6.2 编译打包与部署

项目使用 Maven 构建系统，结构标准化，规避了 IDE 强依赖。

1. **代码编译**：在项目根目录打开终端执行 `mvn clean compile`。
2. **运行程序**：执行 `mvn javafx:run` 即可唤起程序主界面。
3. **独立便携打包**：我们编写了 `package-stable.ps1` 脚本。通过使用 JDK 原生的 `jpackage` 工具，将系统连同精简版 JRE 及所有相关依赖，打包合成为独立的 `DigitalImageManager.exe` 免安装包。用户在无 Java 环境的 Windows 电脑中也能双击即开。

### 6.3 使用指引

1. **初次启动**：双击运行。如未侦测到数据库配置文件 (`database.properties`)，系统将弹出初始化向导。
2. **入库扫描**：在左侧树形目录右键“导入”，选择磁盘文件夹。系统在后台静默建立数据库索引。
3. **智能探索**：在设置页面填写 API Key。在搜索栏尝试输入“帮我找出 2026年拍的，里面有两个人的图片”，系统将依靠大模型与本地数据库的交互呈现结果。
4. **灾难恢复降级（离线模式）**：拔掉网线，系统不再尝试请求 AI，但图片的加载、编辑、幻灯片、本地重命名、基本属性搜索等所有依托本地 PostgreSQL 的功能依然流畅运行。

## 第七章 总结与不足

### 7.1 总结

通过本次《基于 PostgreSQL 的数字图像集成管理系统》课程设计，我们成功地将经典的 GUI 桌面编程与深刻的数据库内核技术相结合。我们验证了将操作系统中原本脆弱的文件体系，全面映射至具备高一致性、事务隔离特性的关系型数据库的可行性。这不仅仅是一个调用外置 API 的套壳应用，而是一个真正由 `PostgreSQL` 驱动底层（运用 CTE、Triggers、Stored Procedures 及 BYTEA）的数据资产管理平台。团队成员在 JDBC 安全规范、HikariCP 连接池优化、数据库模式（Schema）正规化设计等多个维度积累了宝贵的实战经验。

### 7.2 不足与未来展望

由于学时与资源所限，系统在以下维度仍存在改进空间：

1. **云端融合度不足**：目前虽然在数据库中设计了 `cloud_sources` 及 `cloud_images` 的表结构作为未来云端/网盘融合的挂载点，且代码结构留有扩展接口，但在实际 Java 业务层中尚缺乏针对 WebDAV 协议的具体解析。暂未实现完整的主备双活云同步。
2. **人脸识别针对性薄弱**：当前 AI 识别倾向于整图通用自然语言描述，若需构建极高精度的个人相册，后续需引入专业的结构化人脸特征向量（Vector）库及 `pgvector` 插件配合使用。
3. **内存管理**：在超大规模图片目录连续进行幻灯片播放时，JavaFX 的 `WritableImage` 垃圾回收可能不够平滑，需进一步探索底层的按需渲染技术。

未来，我们将围绕上述痛点，继续深挖 PostgreSQL 的拓展性，为打造专业级的个人数字资产托管系统而努力。
